# タスクの変更履歴

タスクは一つの変更イベント履歴を持つ。要件定義・仕様整理・実装手順・実装中の各チャットは、この履歴を通して別フェーズで起きた変更を受け取る。文書の最新版と履歴はフェーズ間で共有する。

## 記録するイベント

最初の対象はタスク文書とフェーズ変更とする。ソースコードや生成物を含むリポジトリ全体の監視は対象に含めない。

| イベント | 内容 |
| --- | --- |
| 文書作成・更新 | 対象の相対パス、変更後の版への参照 |
| 文書削除 | 対象の相対パス、削除前の版への参照 |
| 文書リネーム | 変更前後の相対パス、対象の版への参照 |
| フェーズ変更 | 変更前後のフェーズ |

各イベントはタスク内で順序を比較できるID、発生時刻、変更元のフェーズを持つ。外部エディターなど変更元を特定できない場合は不明として記録し、表示中のフェーズを変更元と推定しない。リネームイベントを定義することは、文書リネームUIを追加する決定とは別とする。

ファイルの内容は版として保存し、イベントから参照する。更新・削除後も過去の本文を確認できるようにする。イベントのファイル名一覧だけでは本文の履歴を代替しない。

## チャットへの引き継ぎ

各フェーズのチャットは、最後にエージェントへ渡したイベントIDをカーソルとして保持する。最後のチャット時刻では判定しない。

1. 送信時に変更履歴の末尾を取得し、その送信の上限IDとする。
2. カーソルより後、上限IDまでのイベントを順序付きで取得する。初回は先頭から取得する。
3. ユーザーの発言とともに、作成・更新・削除・リネーム・フェーズ変更の一覧と対象文書の参照をエージェントへ渡す。
4. エージェントは必要な文書の最新版を読む。過去の内容が必要なら参照先の版を確認する。
5. 渡した範囲に対応するカーソルを保存する。送信時の上限より後のイベントは、生成中に起きた変更も含め、次回に渡す。

取得しただけではカーソルを進めない。送信失敗や受け付けの成否が不明な場合に、未受領の変更を読み飛ばさない。引き継ぎ情報の受領と、モデルが変更内容を理解・解決したことは区別する。

準備フェーズのクリックによる変更だけではエージェントを自動起動しない。「開始」は実装中の会話へ定型依頼を送信し、この引き継ぎ手順を適用する。同じフェーズへの次の送信でも、この取得手順を使う。前のフェーズへ戻っても文書やイベントは巻き戻さず、そのフェーズの会話に新しい変更を渡す。

## 保存と通知

イベントと文書の版はバックエンドに永続化する。ブラウザー未接続の間の変更も、後から取得できるようにする。WSは変更があったことの通知に使い、未受領イベントは保存済み履歴から取得する。

会話本文、文書本文の版、変更イベントはそれぞれ別の役割を持つ。エージェントへの変更引き継ぎカーソルと、フロントエンドの返信パック受領・ハッシュ照合も別に管理する。

## 保存形式と確定手順

タスクフォルダーの `.history/index.json` に形式バージョン1、最後に観測したフェーズ、文書パスとSHA-256の対応、イベント列を保存する。本文の版は `.history/versions/<sha256>.md` に不変ファイルとして保存する。版を先に書き、イベントと観測状態を一つのJSONとしてatomic replaceする。途中終了で残った未参照の版は履歴へ公開しない。

イベントのIDはタスク内で1から増える整数とする。共通項目は `id`、`type`、`at`、`sourcePhase`。文書イベントは `path`、`version`、必要に応じて `previousPath`・`previousVersion`、フェーズ変更は `from`・`to` を持つ。外部編集の `sourcePhase` は null。内容が一致する削除と追加が一対一のときだけリネームとして扱い、曖昧な場合は削除と作成に分ける。

初回の履歴作成では現在存在する文書を最初の版として記録する。それ以前の内容や時刻を推測して作らない。アプリ停止中や無購読時の変更は、一覧・文書取得・イベント取得・送信時の再照合で記録する。観測できなかった中間版は復元しない。フェーズ変更前後にも照合し、途中終了でメタデータと観測フェーズに差が残った場合は次の照合で記録する。

履歴はタスクとともに保持し、自動間引きしない。タスク削除では全フェーズの会話と履歴・版をまとめて削除する。プロジェクト複製では履歴と版を保持し、新しいタスクIDに属する履歴として扱う。会話のCLIセッションと引き継ぎカーソルはリセットする。

## 会話のカーソル

フェーズ別会話JSONの `lastEventId` に、受け付けを確認できた上限IDを保存する。未送信時は0。送信開始時に対象イベントを確定し、`turn/start` の成功応答を受信した後にカーソルを保存する。生成完了は待たない。受け付け後の保存失敗や成否不明ではカーソルを先へ進めず、次回の重複受領を許容する。取得・送信の途中で増えたイベントは、固定した上限より後として次回へ残す。

引き継ぎイベントはエージェントへの入力に添え、ユーザー発言の保存本文には混ぜない。本文の版の参照先も渡し、必要な版を確認できるようにする。

## 取得と通知の契約

`GET /api/tasks/:id/events` は `projectId` と `after`（既定0）、任意の `through`、`limit`（1〜100、既定100）を受け取り、`{events, lastEventId, through, hasMore}` を返す。`through` 省略時は照合後の末尾で固定する。`lastEventId` は返却末尾、空なら `after`。後続ページでも同じ `through` を使う。未知のカーソル・版・対象は404、不正な形式や範囲は400。

`GET /api/tasks/:id/events/versions/:hash?projectId=...` は、そのタスクのイベントから参照される本文の版を `{version, content}` で返す。

WSの `task-events` トピックはタスク全体を対象とし、`task.events.changed` の `{lastEventId}` で変更を通知する。再購読時もHTTPから最新情報を取得する。通知の取りこぼしや重複は保存履歴に影響しない。
