# LLM チャット連携

## 目的と方針

指示書の自動更新や計画・実行の自動化に先立ち、ユーザーが選んだ接続先と Beni の画面で会話できるようにする。最初の実接続は **Codex または ChatGPT 連携**を候補とし、どちらを先に実装・動作確認するかは未決定。接続先は役割と分離し、後から追加・交換できるようにする。

ここでいう Codex は CLI が提供するエージェントとの連携、ChatGPT 連携は Sign in with ChatGPT によって対象ユーザーの利用枠で推論する方式を指す。Codex 自体も ChatGPT アカウントで認証できるため、二つの名前はログインの種類による分類ではない。通信先と認証方式は別の選択肢であり、アプリ自身が管理する ChatGPT 認可と Codex app-server を組み合わせる方式も公式に用意されている。通常の API キーによる OpenAI API は別の認証・利用方法として扱い、自動的に切り替えない。

## 接続方式の候補

### Codex

- Codex app-server を起動し、構造化された通信で初期化する。会話の作成・再開、発言の送信、回答の逐次受信、エラーや承認要求を扱う。会話の継続に必要な接続先の ID を保存する。
- 接続状態とモデル一覧は、使用する実行環境・アカウントに対して確認する。取得したモデル一覧は利用権限の保証として扱わない。
- 認証は接続先の正式な手順に従い、認証情報をブラウザー・会話履歴・ログに表示しない。既存認証の扱いとアカウントごとの分離は実装時に確認する。
- コーディングエージェントにはファイル操作やコマンド実行の機能もある。初期の会話では勝手に変更・実行しないことを前提に、実際に適用できる権限設定と承認要求の扱いを確認する。

### ChatGPT 連携

- 対象となるオープンソースアプリ向けの Sign in with ChatGPT と、許可された利用枠での Responses API 呼び出しを候補とする。利用資格、登録、認可、対応モデル・利用条件は実装時に公式資料で確認する。
- アプリが認可状態を管理し、推論結果を逐次受け取る。認可情報は会話データと分離して安全に保持し、画面・ログに出さない。Codex の認証情報を自動で共有・流用しない。
- 現行プレビューでは Responses API に `store: false` と `stream: true` を指定し、要求ごとに必要な会話履歴を `input` に含める。利用できないフィールドや条件があるため、実装時に最新の公式資料を再確認する。
- 通常の API キーによる Responses API や他の接続先も将来追加できるようにする。ただし接続できないときに別の課金方式へ自動で移行しない。

### Claude Code

- Claude Agent SDK の `query` を使い、部分応答を逐次受け取る方式を候補とする。メッセージのストリーミング入力にも対応し、会話に対応するセッション ID を記録して、再開可能な場合はそのセッションを再開する。
- SDK や実行ファイルの検出、使用するモデル、認証状態、利用可能な利用枠は別々に確認し、実行環境の相違や確認できない状態を画面に反映する。利用する認証・課金方式を別の方式へ自動で切り替えない。
- 会話時に使うツールの権限と承認要求を明示的に扱う。ファイル操作やコマンド実行を伴う場合は、会話との違いを把握し、適用する権限とユーザーへの確認方法を定める。
- 公式資料では、事前承認のない第三者製品による claude.ai ログイン・利用枠の提供を認めず、Agent SDK では API キー方式を案内している。利用者本人が Claude Code を直接利用する方式の条件と一律に同一視せず、Beni の提供形態・認証方法への適用を実装前に確認する。

## 会話と画面

- 接続先・モデルを選び、ユーザー発言と回答を表示する。応答は受信途中も更新し、完了・失敗・中断・結果不明を区別する。
- タスクに対応するチャットとプロジェクトのジェネラルチャットを別の会話として扱い、表示、履歴、接続先の会話 ID が混ざらないようにする。
- 会話本文、送信 ID、接続先、モデル、結果と時刻を保存し、画面の再読み込み後も履歴を確認できるようにする。会話の再開方法は接続方式に合わせる。
- 設定画面では、実行ファイルの検出、認証の状態、モデル一覧、利用枠をそれぞれ区別して表示する。確認できない項目は未確認とし、未取得を利用可能と断定しない。
- 要求が未送信と分かる場合と、送信されたか不明な場合を分ける。結果不明を自動で再送せず、重複送信のリスクを抑える。停止や再接続では、処理が終了したと確認できない限り完了と見なさない。

## 実装順と検証

1. 既存のチャット画面と会話保存を使い、接続先を差し替え可能にする。偽の接続先で送信・逐次表示・履歴・中断を確認する。
2. ユーザーが選んだ最初の接続方式を、設定画面の状態表示から実際の会話まで接続する。初回の実接続・動作確認はユーザーが選んだ接続先と認証方式で行う。
3. 会話の継続や失敗・結果不明の復旧を確認する。その後、指示書の自動更新や計画・実行の流れへ組み込む。追加した接続先が対応していない操作は未接続・未対応として表示する。

プロジェクト／タスク間の混入、二重送信、通信断、途中応答、更新・画面移動後の状態、誤った接続先への自動切替がないことを検証する。実サービスの利用可否とモデルのアクセス権は、実際に選んだ環境で確認する。
