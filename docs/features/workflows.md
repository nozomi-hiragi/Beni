# イベントに対応するワークフロー

タスクの状態変更をプロジェクトイベントとして記録し、対応するアプリ共通のインストラクションをバックグラウンドで実行する。現在の対象は `task.completed`（タスク完了）。上層へのナレッジ反映は、このインストラクションに記述する処理方針とする。

## 責任の分担

- 終了フェーズはタスクの学びをプロジェクトのナレッジへまとめ、確定した版を申告する。
- アプリはタスクの完了と `task.completed` を記録し、対応する実行を登録する。実行の入力には起点のプロジェクト・タスク、確定したナレッジ版、適用するインストラクションの版を保持する。
- `task.completed` インストラクションは Beni 全体で管理する。初期本文には、ナレッジを確認し、再利用できる学びがあれば共通・フェーズ別の指示へ反映する手順を書く。変更不要の判断も認める。本文はインストラクション編集相談から変更できる。
- 実装は実行、参照・更新ツール、権限、結果の確定を担当する。「上層へ流す」という専用イベントや、指示本文とは別の固定プロンプトは追加しない。

## 実行と権限

完了イベントが確定する前にワークフローを実行しない。同じ完了回の登録・再試行で重複した実行を作らず、再起動時に未登録・未確定の処理を復旧する。タスクを再開して再度完了した場合は別の実行とする。

ナレッジは完了時の固定版、ワークフローの指示は実行登録時の固定版を読む。反映先の指示は最新の版を読み、変更時に版の競合を検出する。複数プロジェクトからの変更は直列に実行する。

参照できるプロジェクトと更新できる文書はバックエンドで制限する。インストラクションの文面を変更しても権限は広がらない。ワークフロー自身と編集相談用の指示は自動更新の対象にしない。準備した文書変更と成功結果は同じトランザクションで確定する。変更なしの場合も判断理由を保存する。

ワークフローの失敗でタスク完了を取り消さない。状態と失敗理由を表示し、同じ実行を再試行できる。待機中・実行中は起点タスクの削除を拒否する。

## 実行の記録と閲覧

開始・成功結果の確定・失敗を、それぞれ `workflow.started`・`workflow.completed`・`workflow.failed` としてプロジェクトイベントに記録する。`details` に `workflowJobId`、`eventKey`、`triggerEventId`（未記録ならnull）、`attemptId`（試行ID）を保持する。再試行ではジョブとチャットを再利用し、試行IDを分ける。開始時点で未生成のチャットIDは推測せず、ジョブIDから後で参照できるようにする。結果未確定の開始イベントを成功と扱わない。イベントDBへの書き込みが失敗しても、確定したジョブ結果を変更したり自動再実行したりしない。固定メッセージで記録失敗を通知し、イベントが欠けた場合に成功を推測しない。

データ画面では実行管理情報と会話をチャットにまとめ、イベントから対応チャットと起点イベントへ移動する。実行管理の `instruction_jobs` は維持する。導入前のジョブの開始・終了時刻は不明のままにし、過去の実行イベントを捏造しない。

## 保存と移行

会話は `data/chats/<chatId>.json` に置く。実行IDと会話IDは別の識別子。実行の管理情報はアプリDBに保持し、プロジェクト・タスク・入力の版と結び付ける。完了した実行の会話は起点タスクの削除後もプロジェクトに残す。

旧用途別配置・ハッシュ名の会話は、登録済み実行の所属を照合してチャット管理へ移行する。新旧IDの対応と実行IDへの参照を保存し、会話本文とプロバイダのセッション情報を保持する。検証後に旧ファイルと空ディレクトリを削除する。衝突、リンク、未登録の会話は保全する。[移行仕様](../data/chat-management.md#既存データの移行)

インストラクション画面では「ワークフロー」に「タスク完了」を表示し、本文の参照・フォーカス・編集相談を既存の指示と同じ経路で行う。
