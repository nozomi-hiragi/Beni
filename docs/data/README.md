# データ設計

データの保存責任と識別子を定義します。Beni が管理する永続データはアプリデータ領域に集約します。保存構成・移行・作業フォルダー再指定は [保存データの集約](storage.md) を参照してください。

チャットのID管理と保存先の仕様は [チャット管理](chat-management.md) を参照してください。

## 保存の責任

プロジェクトに属するデータも、アプリデータ領域の `projects/<projectId>.sqlite` に置きます。アプリ側SQLiteはプロジェクトの登録情報、インストラクションの版、インストラクション更新ジョブ、エージェント連携情報を管理します。ブラウザーの表示状態とシェルの実行状態は、永続データと分けます。

| 対象 | 責任を持つ場所 | 保持する情報 |
| --- | --- | --- |
| プロジェクト情報 | アプリデータの `beni.sqlite` の `projects` | ID・名前・作成日時・更新日時と作業フォルダーへの対応 |
| LLMの指示と更新ジョブ | Beni のアプリデータ | 全共通・各フェーズ・編集相談用・イベント用のテンプレートの版と、ワークフローの実行・結果 |
| 指示の編集相談 | Beni のアプリデータ | `chats/<chatId>.json` のアプリ共通会話 |
| エージェント連携情報 | アプリデータの `beni.sqlite` の `agents` | 確認済みの接続・認証状態、実行ファイル、モデル一覧、確認日時、アカウント照合値、利用枠と取得日時 |
| タスク文書とナレッジ | アプリデータの `projects/<projectId>.sqlite` | 文書項目、根拠、引用と文書の版 |
| イベントとワークフロー | アプリデータの `projects/<projectId>.sqlite` | 変更イベント、文書の差分、送信時の文脈、反省会の精査状況、実装とナレッジの終了判定 |
| タスクの識別・状態 | アプリデータの `projects/<projectId>.sqlite` | タスクID、名前、フェーズ、状態、日時 |
| プロジェクトの会話 | アプリデータの `chats/<chatId>.json` | Generalとアーカイブの会話 |
| ワークフローの会話 | アプリデータの `chats/<chatId>.json` | イベント用インストラクションの実行会話 |
| タスクの会話 | アプリデータの `chats/<chatId>.json` | フェーズ別の発言、ツール操作、送信状態、接続先の会話識別子とアーカイブ |
| ブラウザーの表示状態 | フロントエンド | 選択中のタブ、スクロール位置、未確定の受信内容 |
| シェル・操作権 | バックエンドの実行時状態 | プロセス、端末画面、接続ごとの操作権 |

この表の「責任を持つ場所」は保存・復元の境界を示します。作業リポジトリと Beni の保存領域は独立して管理します。会話や実ユーザーデータを公開リポジトリへ自動追加しません。

## データの関係

- 一つのプロジェクトに複数のタスクが属する。
- プロジェクトのジェネラル会話と、各タスクの会話を区別する。
- 一つのタスクに要件・実装計画などの文書が属する。
- 会話には順序を持った発言が属し、各発言が本文やツール操作のパートを持つ。送信ID、同期用のパックID、接続先のセッションIDは用途が異なる。
- ターミナルはプロジェクトに属する。タスクを切り替えてもシェルの生存とは切り離す。

プロジェクトID・タスクID・チャットIDは、次のUUIDv7ベースの独自規則で生成します。ID同士の連結はしません。配置は [保存データの集約](storage.md) に定義します。移動・復元ではIDを維持します。ファイル名や保存先の絶対パスだけで同一データと決めつけません。

## 正本と表示用データ

タスク文書とプロジェクトナレッジはアプリデータ内のプロジェクト別SQLite、インストラクションはアプリ側のSQLiteを正本とします。Markdown本文とブラウザーのプレビューは文書項目から組み立てます。

会話の確定内容はバックエンドに保存します。フロントエンドはパック単位で同期し、確認できた内容を確定済みとして保持します。表示上の確定と、エージェントの実行成功は別の状態です。

パックの形式・ハッシュ・再接続の手順は [チャットのパック同期](../communication/chat-sync.md) と [HTTP API](../communication/http-api.md) を参照します。ここでは通信契約を重複定義しません。

## 復元の原則

- 画面の再読み込みだけで永続データを失わない。
- バックエンド再起動時、完了を確認できない送信を自動再送しない。
- 文書があることだけでタスク名・フェーズ・実行結果を推測して確定しない。
- 一部の保存先が欠けても、残っているデータを上書き・削除して整合させない。
- バックアップと復元では、文書・会話・識別情報の対応を保つ。

シェルの再起動後の復元は対象外です。ライフサイクルと操作権は [ターミナル仕様](../features/terminal.md) に従います。

## IDの共通規則

```text
xxxxxxxx-xxxx-7t00-vxxx-xxxxxxxxxxxx
              ││   └ variant: 8 / 9 / a / b
              │└ 種別: 0 = プロジェクト、1 = タスク、2 = チャット
              └ version: 7
```

第3グループのバージョン番号に続く16進3桁をBeni用に予約します。先頭の1桁を種別、残り2桁を将来用の予約領域とし、未使用部分は `0` で埋めます。

| 対象 | 第3グループ |
| --- | --- |
| プロジェクト | `7000` |
| タスク | `7100` |
| チャット | `7200` |

先頭48ビットのミリ秒時刻とvariantはUUIDv7の配置を維持し、末尾の62ビットは暗号学的乱数で生成する方針です。同一ミリ秒・同一種別のランダム部分は62ビットとなります。衝突時に既存データを上書きしません。IDは認証情報として扱いません。

標準UUIDv7では、この12ビットは `rand_a` として乱数や時刻精度・単調性のために使われます。種別・予約領域への転用はBeni独自の生成規則であり、標準UUIDv7の生成方式に準拠するとは扱いません。一般のUUIDv7生成器の出力をそのまま採用せず、この規則を検証します。独自フィールドを標準の枠内で表すUUIDv8への変更は、この決定には含めません。

参照: [RFC 9562 §5.7](https://www.rfc-editor.org/rfc/rfc9562.html#section-5.7)
