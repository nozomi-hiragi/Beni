# データ設計・移行

保存方式の決定と実装に使う文書です。確定した仕様は [データ設計](README.md) に反映します。この段階ではデータの移動・復元・DB変更は行いません。

## 保存場所ごとの現行形式・検討

- [SQLite](sqlite/migration.md): テーブル、登録情報、ID、旧履歴。
- [プロジェクトの `.beni`](beni/migration.md): 文書、会話、未登録タスク、移動・複製。

現行のアプリの既定保存先はアプリルートの `data/`。`BENI_DATA_DIR` でDBと会話をまとめて変更できます。相対指定は起動時の作業ディレクトリから解決されます。プロジェクトの文書はこの設定では移動しません。

シェル・端末画面・操作権はバックエンドのメモリー上にあり、今回の永続データ移行の対象外です。

## 解決する問題

1. プロジェクト内に文書が残っていても、DBのタスク登録がなければ一覧に出ない。
2. アプリデータだけ、またはプロジェクトだけを移動すると、タスク・会話・文書の対応を失う可能性がある。
3. 別のアプリDBで同じ連番が使われても、同じタスクとは限らない。
4. DBとファイルをまたぐ保存には単一のトランザクションがない。作成途中の失敗を含めた復旧方法が必要。
5. 旧DBのメッセージ・文書と新しい正本が併存している。引き継ぎと廃止の条件を明示する必要がある。

## 共通で決めること

アプリ側SQLiteは `projects` だけを残し、タスク・文書・会話はプロジェクトの `.beni` に移す方針を確定しました。移行対象は旧DBの `tasks`・`messages`・`documents` とアプリ側の `data/chat/` です。既存Markdownは上書きせず、移行・照合後に旧データを削除します。

`.beni` は `project.json`、`tasks/<UUIDv7>/task.json` と文書、`chat/general.json` と `chat/<UUIDv7>.json` で構成します。プロジェクト・タスクIDには共通ID規則を適用します。既存の整数プロジェクトIDも対応表を保持して移行します。

メタデータは整数の `version`、文字列の `id`・`name`、UTC日時の `createdAt`・`updatedAt` を持ち、タスクには `phase`・`status` を加えます。名前の正本は `project.json` です。移動・復元ではIDを維持し、別プロジェクトとしての複製ではプロジェクト・タスクのIDを再発行します。複数起動の扱いは [Beni全体の動作条件](../next-agent-plan.md#動作条件) に従います。

残る検討は未対応形式・過去日時不明時の扱い、複製時の参照更新、バックアップの具体的な手順です。今回は文書の更新に留め、実データの移行・削除は行いません。

## 実装の順序案

1. メタデータの検証・複製時の参照更新の手順を定義する。
2. 保存形式のバージョンと、旧IDから新IDへの対応方法を定義する。
3. 既存データを読み取りだけで検査し、欠落・衝突・未登録文書を報告する。
4. バックアップを確保して移行し、件数・参照・本文の一致を確認する。成功確認前に旧データを削除しない。
5. 一覧・文書・会話を新しい正本へ接続し、旧形式の扱いを整理する。

## 検証項目

- 新規作成後、再起動して同じタスク・会話・文書を参照できる。
- 文書だけ、登録だけ、会話だけが残った状態を区別できる。
- 同じ番号を持つ別プロジェクト・別DBのデータが混ざらない。
- プロジェクトの移動・再登録・複製で、決定したIDの規則を保つ。
- 保存途中の失敗と移行の再実行で、上書き・重複登録・本文欠落を起こさない。
- 生成途中・結果不明の会話と、確定済みパックの状態を維持する。
- バックアップ復元後、ファイルの存在だけでなく内容と参照関係も一致する。

実データによる試行は通常のテストに含めず、架空のデータで検証します。
