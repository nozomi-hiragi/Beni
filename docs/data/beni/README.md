# プロジェクトの .beni

保存仕様を定義します。

プロジェクト内で完結するデータはプロジェクト側に配置します。タスクの要件・実装計画などの文書とプロジェクトナレッジは `.beni/project.sqlite` を正本にします。Markdown本文は文書項目から組み立てます。

タスクの識別情報・名前・フェーズ・状態、文書、ジェネラル・タスク会話を `.beni` にまとめます。プロジェクトを移動すると、これらのデータも一緒に移動する構成とします。

## ディレクトリ構成

```text
.beni/
├── project.json                  プロジェクト情報
├── project.sqlite                 プロジェクトイベント・文書の版・ナレッジ・精査の進捗
├── chat/
│   ├── general.json              ジェネラル会話
│   ├── history/                  リセット前のジェネラル会話（会話ID.json）
│   ├── workflow-jobs/             インストラクション更新ジョブの会話
│   └── <taskId>/
│       ├── <phase>.json          フェーズ別のタスク会話
│       └── history/              リセット前のフェーズ会話・前回の終了会話（会話ID.json）
└── tasks/
    └── <taskId>/
        └── task.json             タスク情報
```

メタデータと会話はJSON、文書と変更履歴はSQLiteに保存します。新規タスクは `requirements.md`、`documents.md`、`implementation.md` の初期版をDBに作成します。

既存タスクの文書を初めてDB文書として参照するとき、タスクフォルダー直下の英小文字で始まる英小文字・数字・ハイフンの `.md` ファイルを取り込み、同名の初期テンプレートより優先します。プロジェクトナレッジの初回参照時には、既存の `.beni/knowledge.md` があれば取り込みます。取り込む本文は1 MiB以下のUTF-8とし、シンボリックリンクやハードリンクを拒否します。取り込み済みの記録と文書の版は同じトランザクションで保存し、元のファイルも保全します。取り込み後の読み書きにはDBを使います。

会話の保存内容・更新規則は [chat/ の仕様](chat.md) を参照します。

## タスクID

タスクIDは [共通ID規則](../README.md#idの共通規則)に従うUUIDv7ベースのID（第3グループ `7100`）とし、`task.json` のID、タスクフォルダー名、chat配下のタスクフォルダー名に同じ値を使います。プロジェクトIDを連結した別のタスクUIDは作りません。

UUIDv7は生成時刻を含むため、IDによって時刻順に並べやすい形式です。ただし複数環境の時計や同時生成を含む厳密な操作順序の保証には使いません。作成日時は `createdAt` にも記録します。日時はUTCのISO 8601形式で記録します。

タスク一覧は `tasks/*/task.json` を読み取って構成します。プロジェクトIDは同じ共通規則のプロジェクト用ID（第3グループ `7000`）とし、`project.json` の `id` に保存します。移動・再登録ではIDを維持します。

文書が残っていることだけで、タスク名・フェーズ・実行結果を推測して確定しません。登録が欠けても残存ファイルを上書き・削除しません。

プロジェクト内に置くことと、Gitに含めることは別です。実ユーザーデータを公開リポジトリへ自動追加しません。

## メタデータ

`version` はJSONの保存形式を示す整数で、初版は `1` とします。更新回数ではありません。新規作成時の `createdAt`・`updatedAt` はUTCのISO 8601形式（末尾 `Z`）で保存します。復元時に過去日時を確認できない場合は `null` を保存し、IDの生成時刻を過去の作成日時として代用しません。以下は架空のデータです。

### project.json

```json
{
  "version": 1,
  "id": "019a5000-0000-7000-8000-000000000001",
  "name": "サンプルプロジェクト",
  "createdAt": "2026-01-01T00:00:00.000Z",
  "updatedAt": "2026-01-01T00:00:00.000Z"
}
```

プロジェクト名はこの `name` が正本です。SQLiteの名前は一覧表示用のコピーとして同期します。絶対パスは `project.json` に保存せず、アプリ側の登録情報に持たせます。

### task.json

```json
{
  "version": 1,
  "id": "019a5000-0000-7100-8000-000000000002",
  "name": "サンプルタスク",
  "phase": "requirements",
  "status": "idle",
  "createdAt": "2026-01-01T00:00:00.000Z",
  "updatedAt": "2026-01-01T00:00:00.000Z"
}
```

タスクには共通項目に加え `phase`・`status` を持たせます。例は初期状態です。状態の値・遷移はワークフロー仕様と合わせ、保存形式だけを理由に増やしません。所属プロジェクトは `.beni` の配置から決まり、タスクIDにプロジェクトIDを連結しません。

### タスクの更新日時

`updatedAt` は、タスク名、フェーズや状態、タスク会話、タスク文書を更新したときに記録します。タスク会話では発言・応答・ツール結果などを保存したとき、DB文書では版を保存したときに更新します。ジェネラル会話とプロジェクトナレッジの更新はプロジェクトに属するため、タスクの更新日時には反映しません。

旧Markdownの取り込み前は、タスク一覧取得時に文書の追加・本文変更・削除を照合します。初回の照合では比較の基準だけを記録し、以前の更新日時を保ちます。`task.json` の `documentBaseline` に各文書のファイル名、本文のSHA-256、ファイル更新時刻（ミリ秒）を記録します。変更時刻が分かる場合はその時刻を、削除など変更時刻を特定できない場合は検出時刻を使います。移行済みタスクではこの照合を行いません。

## 移動・復元

移動・再登録・バックアップ復元ではプロジェクトIDとタスクIDを維持します。

複数起動の扱いは [Beni全体の動作条件](../../specification.md#動作条件) に従います。

## 文書だけ残ったタスク

`task.json` がなく、旧Markdownファイルが残ったタスクフォルダーは、名前を `Unknown` として自動登録・復元します。現行形式のフォルダー名ならタスクIDを維持し、旧形式の数字だけのフォルダー名には新しいIDを割り当てます。元の文書は維持し、本文からタスク名や過去のフェーズ・状態・日時を推測しません。復元後の初期値は `phase: requirements`・`status: idle` とし、不明な日時は `null` とします。DBに残る文書から `task.json` を自動生成する処理はありません。

## 反省会と終了の保存状態

反省会のphaseは `retrospective`。初回到達時に `retrospective.md` の初期版をDBに用意し、既存の版があれば引き継ぎます。「タスク完了」を押すと `phase: finalization`、`status: idle` で終了処理に入り、ナレッジ版を確定してインストラクション更新を予約すると `status: completed` になります。ナレッジを確定できなければ反省会へ戻ります。完了後に再開すると `phase: retrospective`、`status: idle` に戻ります。旧形式の `retrospective / completed` のタスクも読み取れます。

プロジェクト共通のナレッジ文書 `knowledge.md` は、終了フェーズで確定したDB内の版を次のタスクに引き継ぎます。
