# プロジェクトデータ

プロジェクトデータはアプリデータの `projects/<projectId>.sqlite` に保存します。旧 `.beni` からの移行と検証後の削除は [保存データの集約](../storage.md) に従います。

保存仕様を定義します。

タスクの要件・実装計画などの文書とプロジェクトナレッジは、アプリデータ内の `projects/<projectId>.sqlite` を正本にします。Markdown本文は文書項目から組み立てます。

タスクの識別情報・名前・フェーズ・状態と文書をプロジェクトIDごとのDBにまとめます。作業フォルダーの移動・消失後もデータを保持します。

## ディレクトリ構成

```text
projects/
└── <projectId>.sqlite               タスク情報、文書、版、根拠、イベント、ワークフロー
```

会話とアーカイブはアプリ共通の `chats/<chatId>.json` に置き、所属をアプリDBで管理します。

会話はJSON、タスク情報・プロジェクト情報・文書・変更履歴はSQLiteに保存します。新規タスクは `requirements.md`、`documents.md`、`implementation.md` の初期版をDBに作成します。

既存タスクの文書を初めてDB文書として参照するとき、タスクフォルダー直下の英小文字で始まる英小文字・数字・ハイフンの `.md` ファイルを取り込み、同名の初期テンプレートより優先します。プロジェクトナレッジの初回参照時には、集約先にコピーした旧 `knowledge.md` があれば取り込みます。取り込む本文は1 MiB以下のUTF-8とし、シンボリックリンクやハードリンクを拒否します。取り込み済みの記録と文書の版は同じトランザクションで保存し、元のファイルも保全します。取り込み後の読み書きにはDBを使います。

会話の保存内容・更新規則は [会話の保存仕様](chat.md) を参照します。

## 完了イベントの登録復旧

タスク完了の保存中はプロジェクトDBに `pendingCompletion`（完了回のID、ナレッジ版、接続先とモデル）を一時的に記録する。完了イベントを確定し、アプリDBに同じ完了回の実行を登録した後で取り除く。途中停止時は同じ記録から復旧し、会話や完了イベントを重複作成しない。この記録が残っている間は、実行登録を復旧してからタスクの再開・削除を判定する。

## タスクID

タスクIDは [共通ID規則](../README.md#idの共通規則)に従うUUIDv7ベースのID（第3グループ `7100`）とし、プロジェクトDBのタスクIDとして使います。会話はアプリ共通のチャット管理でID参照します。プロジェクトIDを連結した別のタスクUIDは作りません。

UUIDv7は生成時刻を含むため、IDによって時刻順に並べやすい形式です。ただし複数環境の時計や同時生成を含む厳密な操作順序の保証には使いません。作成日時は `createdAt` にも記録します。日時はUTCのISO 8601形式で記録します。

タスク一覧は各プロジェクトDBから取得します。プロジェクトIDは同じ共通規則のプロジェクト用ID（第3グループ `7000`）とし、アプリDBの `projects.id` に保存します。移動・再登録ではIDを維持します。

文書が残っていることだけで、タスク名・フェーズ・実行結果を推測して確定しません。登録が欠けても残存ファイルを上書き・削除しません。

保存先は作業リポジトリと独立しています。実ユーザーデータを公開リポジトリへ自動追加しません。

## メタデータ

旧JSONの `version` は保存形式を示す整数で、初版は `1` です。新規作成時の `createdAt`・`updatedAt` はUTCのISO 8601形式（末尾 `Z`）で保存します。復元時に過去日時を確認できない場合は `null` を保存し、IDの生成時刻を過去の作成日時として代用しません。以下は架空のデータです。

### プロジェクト情報

ID・名前・作成日時・更新日時と作業フォルダーは、アプリDBの `projects` を正本として保存します。プロジェクトDBには所属IDを保持し、DBファイル名のIDと照合します。`project.json` は通常の保存には使いません。

既存JSONは内容をDBへ引き継ぎ、読み戻しで確認した後に削除します。日時が不明な場合は `null` を維持します。旧 `.beni` の取り込みでは従来のJSONも読み取ります。[プロジェクト情報の集約](../storage.md#プロジェクト情報の集約)

### タスク情報

保存項目の例です。通常の保存先はプロジェクトDBです。

```json
{
  "id": "019a5000-0000-7100-8000-000000000002",
  "name": "サンプルタスク",
  "phase": "requirements",
  "status": "idle",
  "createdAt": "2026-01-01T00:00:00.000Z",
  "updatedAt": "2026-01-01T00:00:00.000Z"
}
```

タスクには共通項目に加え `phase`・`status` を持たせます。例は初期状態です。状態の値・遷移はワークフロー仕様と合わせ、保存形式だけを理由に増やしません。所属プロジェクトは保存領域のプロジェクトIDから決まり、タスクIDにプロジェクトIDを連結しません。

### タスクの更新日時

`updatedAt` は、タスク名、フェーズや状態、タスク会話、タスク文書を更新したときに記録します。タスク会話では発言・応答・ツール結果などを保存したとき、DB文書では版を保存したときに更新します。ジェネラル会話とプロジェクトナレッジの更新はプロジェクトに属するため、タスクの更新日時には反映しません。

旧Markdownの取り込み前は、タスク一覧取得時に文書の追加・本文変更・削除を照合します。初回の照合では比較の基準だけを記録し、以前の更新日時を保ちます。タスク情報の `documentBaseline` に各文書のファイル名、本文のSHA-256、ファイル更新時刻（ミリ秒）を記録します。変更時刻が分かる場合はその時刻を、削除など変更時刻を特定できない場合は検出時刻を使います。移行済みタスクではこの照合を行いません。

## 移動・復元

移動・再登録・バックアップ復元ではプロジェクトIDとタスクIDを維持します。

複数起動の扱いは [Beni全体の動作条件](../../specification.md#動作条件) に従います。

## 文書だけ残ったタスク

DBへの移行前に `task.json` がなく、旧Markdownファイルが残ったタスクフォルダーは、名前を `Unknown` として自動登録・復元します。現行形式のフォルダー名ならタスクIDを維持し、旧形式の数字だけのフォルダー名には新しいIDを割り当てます。元の文書は維持し、本文からタスク名や過去のフェーズ・状態・日時を推測しません。復元後の初期値は `phase: requirements`・`status: idle` とし、不明な日時は `null` とします。復元結果はDBに保存します。移行済み・削除済みのタスクを残存フォルダーから重複登録しません。

## 反省会と終了の保存状態

反省会のphaseは `retrospective`。初回到達時に `retrospective.md` の初期版をDBに用意し、既存の版があれば引き継ぎます。「タスク完了」を押すと `phase: finalization`、`status: idle` で終了処理に入り、ナレッジ版を確定すると `status: completed` になり、`task.completed` のイベントに対応するワークフローを登録します。ナレッジを確定できなければ反省会へ戻ります。完了後に再開すると `phase: retrospective`、`status: idle` に戻ります。旧形式の `retrospective / completed` のタスクも読み取れます。

プロジェクト共通のナレッジ文書 `knowledge.md` は、終了フェーズで確定したDB内の版を次のタスクに引き継ぎます。

保存と移行の詳細は [タスク情報のDB集約](../task-management.md) に従います。
