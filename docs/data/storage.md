# 保存データの集約

チャットの保存先とID参照は [チャット管理](chat-management.md) に従います。

Beni が管理する永続データをアプリデータ領域に集約する。本書は保存構成、旧 `.beni` からの移行、作業フォルダーの再指定を定義する。

## 保存構成

保存先のルートは `BENI_DATA_DIR`、未指定なら Beni ルートの `data/` とする。相対指定は起動時の作業ディレクトリから解決する。プロジェクトに属するデータもこのルートに含める。

```text
data/
├── beni.sqlite                   プロジェクト登録、インストラクション、ジョブ、チャット参照
├── chats/                        全用途の <chatId>.json とアーカイブ
├── instruction-editor/           編集相談の作業先
└── projects/
    └── <projectId>.sqlite         タスク情報、文書、版、根拠、ナレッジ、イベント、ワークフロー状態
```

プロジェクトデータの集約では既存の SQLite・JSON の保存形式を維持し、プロジェクト単位の保存先を移す。プロジェクトDBはイベントIDの採番、差分の連鎖、文書の版を保つ単位とする。インストラクションと更新ジョブはアプリDBに置く。

新規プロジェクトはアプリデータ内で初期化する。作業フォルダーにはソースコードや成果物を置き、Beni の保存処理による `.beni` の新規作成は終了する。

## プロジェクトDBの配置

新規プロジェクトは `projects/<projectId>.sqlite` を直接作成する。DB内の所属IDとファイル名・登録IDを照合する。通常のタスク・文書・イベント操作ではプロジェクト専用のディレクトリを作成しない。SQLiteのWALやSHMなどの付随ファイルは同じDBファイル名に対応させる。

旧 `projects/<projectId>/project.sqlite` はBeni停止中に `bun src/backend/migrate-projects.ts` で移行する。保存先は通常起動と同じ `BENI_DATA_DIR` を使う。旧チャットとタスクJSONも残っている場合は、プロジェクトDB、チャット、タスクJSONの順に専用コマンドで移行する。

1. 所属ID、ファイル種別、既存の移行先との競合を検証する。リンクや別IDのDBを拒否する。
2. WALを含むSQLiteの復旧・チェックポイントと整合性検査を行い、DBの全テーブル・レコードを保持した移行先を確定する。
3. 移行先を読み戻し、タスク、文書版、イベント、ナレッジ、ワークフロー状態とチャット参照を検証する。
4. 検証済みの旧DBと不要になった付随ファイルを削除し、空になった旧プロジェクトフォルダーも削除する。管理外ファイルや未取り込み文書が残る場合は保全する。

移行元と移行先が併存する場合は移行記録と内容で再開を判定する。異なるDBを上書きしない。途中停止や再実行によってイベントやタスクを作り直さない。移行後に旧ディレクトリがなくても通常起動・一覧・文書取得・会話再開・タスク操作が成立することを確認する。

## 正本と識別子

| 対象 | 正本・参照方法 |
| --- | --- |
| プロジェクトID・名前・日時 | アプリDBの `projects`。プロジェクトDB内の識別情報とDBファイル名・登録IDを照合する |
| 作業フォルダー | `beni.sqlite` の `projects.folder`。プロジェクトIDに対応する実行先の絶対パス |
| 一覧用のプロジェクト名 | 正本の `projects.name` をそのまま使う |
| タスク情報 | `projects/<projectId>.sqlite` のタスク情報 |
| 文書・ナレッジ・変更履歴 | `projects/<projectId>.sqlite` |
| Generalの会話・アーカイブ | `chats/<chatId>.json`。所属と現行／アーカイブはアプリDBで管理 |
| 更新ジョブの会話 | `chats/<chatId>.json`。アプリDBで実行IDと対応付ける |
| タスク会話・プロバイダ別の再開情報 | `chats/<chatId>.json`。アプリDBでタスク・フェーズと対応付ける |

IDの生成規則、文書の版、イベントID、発言ID、送信ID、パックIDは維持する。名前や作業フォルダーのパスからプロジェクトの同一性を推測しない。プロジェクトに属するデータの読み書きは、登録されたプロジェクトIDから保存先を解決する。

イベントが保持する `.beni/tasks/<taskId>/<name>` や `.beni/knowledge.md` は既存文書の論理名として引き続き扱う。保存済みの引用、差分、ハッシュを維持し、物理ファイルへのアクセスではプロジェクトIDと文書識別子から保存先を解決する。

## 作業フォルダーとの関係

作業フォルダーとデータ保存先を独立して管理する。ターミナルやエージェントの作業ディレクトリには、登録済みの作業フォルダーを渡す。文書・イベント・会話の取得にはアプリデータ内の保存先を使う。

作業フォルダーが見つからない場合でも、プロジェクト、タスク、文書、会話、履歴を閲覧できる。作業フォルダーを使うチャットの送信、ワークフローの新規実行、ターミナル起動は、保存先の再指定が完了するまで開始できない。取得時の復旧処理も作業フォルダー不在時に実行を始めない。

### 移動後の再指定

既存プロジェクトをIDで指定し、作業フォルダーの登録先を変更する操作を設ける。初回実装の操作場所はホームのプロジェクト選択欄の「作業フォルダーを変更」とし、既存のフォルダー選択を使う。

- 移動先の存在・ディレクトリ種別と、他プロジェクトへの登録済みパスとの重複を検証する。
- 対象プロジェクトのチャット、保守操作、ワークフロー、更新ジョブ、ターミナルが動いている間は変更できない。サーバーでも実行開始と排他的に検証する。
- 同じプロジェクトIDとデータを保持し、変更するのは作業フォルダーへの対応とする。旧フォルダーの消失を必須条件にしない。
- 再指定先に別IDの旧 `.beni` があれば衝突として止める。同じIDでも移行確定後は旧データを再取り込みしない。
- CLIの既存セッションが元の作業フォルダーに結び付いている場合は再指定後の再開に使用しない。保存済み会話と発言当時の再開IDは保持し、次の送信は既存の新規セッション・会話引き継ぎの経路を使う。コンテキスト使用量は未取得に戻す。

新規登録と既存プロジェクトの再指定を別の操作として扱う。旧 `.beni` のないフォルダーを新規登録した場合は新しいIDを生成し、既存の同名プロジェクトへ自動で結び付けない。

## 既存データの移行

旧 `.beni` の取り込みでは、まず次の手順で旧プロジェクト領域を集約する。その後、プロジェクトDB・チャット・タスク情報の順に本書の最終配置へ移す。移行確定前は、そのプロジェクトへのチャット・編集・自動ジョブ・端末操作を開始しない。Beni が停止した状態から移行を始め、一つのバックエンドで処理する。

1. 登録IDと旧 `project.json`、タスクのIDと所属、保存ファイルの種類を検証する。シンボリックリンク・ハードリンクなど、既存の保存規則に反するデータを拒否する。
2. 集約先と同じファイルシステムの一時ディレクトリへコピーする。旧 Markdown、会話アーカイブ、移行管理情報、削除処理のジャーナルを含む旧保存領域を保全する。既知のデータ以外の残存物も削除対象として推測しない。
3. SQLite は本体・WAL・ジャーナルを複製し、コピー先でSQLiteの整合性検査とチェックポイントを行う。移行元の指紋がコピー前後で一致することを確認し、DB本体だけのコピーでは完了としない。旧 `events.sqlite` はコピー先で既存の互換処理を行い、両DBが併存していれば衝突として扱う。
4. コピー元が途中で変化していないこと、JSONの内容、IDと参照、DBの整合性と保存レコードを検証する。会話の件数・順序・パックID、文書版、イベントの末尾・差分・引用、ジョブの参照を保持する。未対応形式はエラーとして残す。
5. 検証済みのディレクトリを `projects/<projectId>/` として確定し、アプリDBの `project_storage` に移行完了を記録する。ディレクトリ確定とDB更新の間で停止しても再開できるよう、対象IDと検証結果を持つ移行記録を残す。
6. チャット・タスク・DBの配置移行を完了してから通常の読み書きを開始する。再起動時も移行記録から同じ保存先を選び、旧 `.beni` への書き込みや再取り込みを行わない。

移行元・移行先の両方がある場合は、移行記録と内容を照合して再開する。確認できない集約先は上書きせず、衝突として停止する。コピー中の失敗では元データを保全し、不完全なコピーを通常の保存先として使わない。 検証済みコピーからの再開では、移行元の内容に加えてファイルの実体も照合する。検証後に別ファイルシステムへコピーし直した移行元は自動で同一視せず、データを残して停止する。

登録済みの旧フォルダーが見つからず、集約データもまだない場合は「移行元が見つかりません」と表示する。空のプロジェクトとして初期化せず、移行元の再指定後に同じIDで続行する。一部の移行失敗で、移行済みの他プロジェクトの閲覧を妨げない。

登録のない旧 `.beni` はフォルダーを明示的に登録した時点で同じ移行処理を行う。移行済みIDの別コピーを登録した場合は既存データへ自動マージせず、作業フォルダーの再指定へ案内する。

移行先の読み戻しと整合性を検証し、移行完了を記録した後、検証済みの旧データを自動削除する。削除前にも移行元の変更有無を照合する。管理外のファイルは移行先の `.migration-extras/` に退避コピーし、旧ファイルは削除しない。移行元の変更や検証失敗がある場合も元データを残す。削除の途中で停止した場合は、移行記録を使って未削除分の検証と後片付けを再開する。

保存先の移行と、旧 Markdown・会話形式の変換は区別する。保存先の移行だけで新しい発言・文書版・イベントを生成せず、日時も維持する。形式の取り込み・復旧が必要な場合は、コピー先で既存の互換規則を適用する。完了を確認できない送信の自動再送は行わない。

### 会話の配置変更

旧用途別の会話とアーカイブを `chats/<chatId>.json` に移し、参照をアプリDBに集約する。旧IDから新しい `7200` IDへの対応を保存し、過去イベントの参照も解決する。検証後に旧ファイルと空の専用フォルダーを削除する。詳細は [チャット管理](chat-management.md#既存データの移行) に従う。

## プロジェクト情報の集約

`project.json` は廃止し、新規プロジェクトでは作成しない。ID・名前・作成日時・更新日時はアプリDBの `projects` に集約する。更新日時はプロジェクト情報の更新時刻であり、タスクや会話の活動時刻とは区別する。保存領域の取り違えを検出するため、プロジェクトDBには所属プロジェクトのIDを保持する。

既存の `project.json` はID・名前・日時とファイル種別を検証し、アプリDBとプロジェクトDBへ引き継ぐ。保存結果を読み戻して一致を確認した後に旧JSONを削除する。元の日時を維持し、不明な日時は `null` のまま保存する。途中停止からの再開で重複登録や新しいDB値の上書きを起こさない。破損・所属不一致・リンク・競合を検出した場合は旧ファイルを保全する。

旧作業フォルダーの `.beni/project.json` は過去データの取り込み・登録照合に限って読み取る。集約後の通常の読み書きやタスク削除の復旧は、このJSONに依存しない。

## タスク情報の集約

タスク情報をプロジェクトDBに保存する。旧 `task.json` の読み戻し検証後に旧JSONを削除し、空のタスクフォルダーを片付ける。途中停止の復旧と削除済みタスクの再取り込み防止は [タスク情報のDB集約](task-management.md) に従う。

## エージェント連携情報の集約

エージェント連携情報と利用枠は `beni.sqlite` の `agents` にまとめる。登録されたエージェントの表示名を保存し、接続情報が未確認の行では確認日時を未記録とする。既存の利用枠から接続情報や確認日時を推測しない。保存項目と再確認の条件は [SQLite](sqlite/README.md) を参照する。

旧 `agent_usage_cache` はトランザクション内で利用枠とアカウント照合値を引き継いでから廃止する。既存の `agents` の値を優先し、移行を繰り返しても新しい値を上書きしない。旧 `rate-limits-codex.json`・`rate-limits-claude.json` は形式の版・アカウント照合値・利用枠を検証して取り込む。DB保存の確定と読戻しを確認できた旧ファイルだけ削除する。壊れたキャッシュや移行・保存の失敗では旧データを保持する。保存に失敗しても取得済みの値は画面に表示する。

## バックアップと復元

バックアップの単位はアプリデータ領域全体とする。アプリDB、プロジェクト別DB、メタデータ、会話を揃えて保存する。Beni を停止してコピーする方法を基本とし、動作中の単純なファイルコピーで整合性を保証しない。

`BENI_DATA_DIR` の変更は参照ルートの変更とする。既存データを使い続ける場合は停止中にデータ領域全体を移す。設定変更だけで別ルートから自動探索・取り込みは行わない。

別環境への復元ではIDを維持し、作業フォルダーをその環境のパスへ再指定する。CLIの認証とプロバイダ自身の会話保存は外部管理であり、Beni のバックアップだけでセッション再開できるとは扱わない。プロジェクト単位のエクスポート・インポートUIは別途検討する。

## データ画面との関係

所属の「アプリ共通」「各プロジェクト」は論理的な分類として維持する。一覧・詳細では集約後の保存元を表示する。取得時に作業フォルダーの存在を要求せず、所属IDと集約先のデータを照合する。

現在のデータ画面は架空データの表示モックであり、モック内の旧保存パスは実データへの接続先ではない。実機能の実装時に本仕様の配置と揃える。[データ画面の仕様案](../screens/data.md)

## 検証条件

- 新規プロジェクトのタスク・会話・文書・履歴がアプリデータ内に保存され、作業フォルダーに `.beni` が作られない。
- 作業フォルダーの消失・移動後も履歴を閲覧でき、再指定後は同じIDで作業を続けられる。別プロジェクトへの混入がない。
- 現行形式・旧形式・WALが残るDB・アーカイブ・削除ジャーナルを含むデータを移行できる。
- コピー・検証・ディレクトリ確定・移行記録更新の各段階で停止しても、再試行で重複や欠損を起こさない。
- 壊れたデータ、重複ID、書き込み失敗、容量不足、移行元の変化、リンクを検出し、元データと既存の集約データを保全する。
- 移行完了後に旧 `.beni` を取り除いても通常の読み書き・履歴参照・再起動が成立する。
- プロバイダのセッション情報を保持し、フォルダー再指定時には旧作業先へ再開しない。移行処理自体では実サービスを呼ばない。

実装時は架空データと偽エージェントで移行・通常操作を検証し、標準の `bun run test` を実行する。
