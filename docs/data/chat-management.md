# チャット管理

チャットの保存先と参照方法を定義する。用途別の旧 `.chat.json` は移行元として扱う。

## IDと保存先

すべてのチャットを `BENI_DATA_DIR/chats/<chatId>.json` に保存する。既定のルートでは `data/chats/` となる。General、タスクの各フェーズ、ワークフロー実行、インストラクション編集相談、アーカイブを同じフォルダーで管理する。

チャットIDは [共通ID規則](README.md#idの共通規則) の第3グループを `7200` として生成する。チャットJSON自身の `chatId` とファイル名のIDは一致させる。表示名、プロジェクト名、フェーズ名をファイル名に含めない。表示名を変更してもIDと保存先は変わらない。

BeniのチャットIDは会話を通して固定する。プロバイダやモデルの切り替え、セッションの再作成、圧縮では変更しない。プロバイダ固有のセッションIDは、引き続きJSON内のモデル別情報に保存する。

## 保存責任と参照

チャット管理がIDの発行、JSONの読み書き、一覧取得、削除を担当する。各機能はチャットIDを渡して操作する。ファイルパスの組み立てと移行処理はチャット管理に集約する。

参照はアプリDB `beni.sqlite` に集約し、用途と所有者から現在のチャットIDおよびアーカイブのIDを解決する。参照には用途、必要なプロジェクトID・タスクID・フェーズ・ワークフロー実行ID、現行／アーカイブの区分を保持する。

| 用途 | 参照の単位 |
| --- | --- |
| General | プロジェクトID |
| タスク会話 | プロジェクトID、タスクID、フェーズ |
| ワークフロー会話 | ワークフロー実行ID |
| インストラクション編集相談 | アプリ共通の編集相談 |

同じ用途・所有者に現行チャットは一つとする。ワークフロー実行IDとチャットIDは独立させ、既存のジョブ記録から対応を引けるようにする。プロジェクトへの所属とワークフローのイベント名は参照情報から解決する。

IDでの取得時にも所有者と操作権を照合する。参照先ファイルの欠落、JSON内のID不一致、異なる所有者への結び付けはエラーとする。欠落した既存チャットを空の会話として上書きしない。

## 会話内容とライフサイクル

発言、パート、プロバイダとモデルの辞書、選択モデル、セッション、コンテキスト使用量は既存の [会話JSON](beni/chat.md) の契約を引き継ぐ。用途別の追加情報も保持する。今回の移行で変更する会話識別子には `chatId` を使い、送信ID・発言ID・パックIDは維持する。

- チャットがまだ存在しない用途では、必要時にIDを発行し、JSONと参照を作成する。同時作成は用途・所有者ごとに排他制御する。
- アーカイブでは既存チャットのIDとファイルを維持し、参照をアーカイブへ変更する。次の会話には新しいIDを発行する。
- クリアなどの既存操作で新しい会話を開始する場合も、旧会話の保持条件に従って参照を更新する。
- タスク削除時はタスク会話とそのアーカイブを削除対象にする。処理済みワークフローの会話は従来どおりプロジェクトに保持する。
- チャット管理のプロジェクト単位削除は、そのプロジェクトに属する会話を対象にする。プロジェクト削除の画面・APIの新設は今回の対象に含めない。アプリ共通の編集相談は独立して保持する。
- 実行中の会話は削除できない。参照が見つからないファイルを、閲覧や起動だけで自動削除しない。

JSONの保存は一時ファイルへの書き込みと置換を使う。JSONとDBの更新をまたぐ作成・アーカイブ・削除は操作記録を残し、途中停止後に同じ処理を再開できるようにする。新規作成ではJSONの確定後に参照を公開し、削除では削除対象を記録してから処理する。通常の参照に不完全なデータを公開しない。

## 既存データの移行

Beniを停止した状態で `bun src/backend/migrate-chats.ts` を実行し、現行会話とアーカイブを含む全チャットを移行する。保存ルートは通常起動と同じ `BENI_DATA_DIR` を使う。通常起動では未移行・移行途中の会話を検出して停止し、専用コマンドを案内する。移行はエージェントへの送信を伴わない。

1. 用途別の保存先、会話JSON、DBやイベントにある会話参照を調べ、所有者と対応を検証する。重複した旧IDを無条件に一つの会話へまとめない。
2. 旧保存先・所有者・旧会話IDと新しい `7200` のチャットIDとの対応を永続化する。再試行では同じ対応を使用する。
3. `chats/<chatId>.json` を作り、会話IDとそれを参照する項目を更新する。発言数・順序・本文・パート・日時・モデル情報・再開情報を保持する。
4. 現行／アーカイブの参照、ジョブとの対応、イベントや同期情報の会話参照を照合する。ハッシュで保護された過去イベントは書き換えず、旧IDとの対応を使って新IDへ解決する。
5. 保存先を読み戻して内容と全参照の解決を検証し、移行完了を記録する。移行中は対象の送信・編集・自動ジョブを開始しない。
6. 検証済みの旧チャットファイルを削除する。空になった旧チャット専用フォルダーも削除する。管理外ファイルや検証に失敗したデータは保全する。

既存の `7200` IDが正しい場合は維持する。移行先が存在する場合は移行記録と内容を照合し、不一致なら上書きせず停止する。削除直前にも移行元が変化していないことを確認する。途中停止後は記録から続行し、重複した会話の生成や旧データの再取り込みを防ぐ。

## 実装時の検証条件

- すべての用途の会話が一つの `chats/` に保存され、IDで取得できる。
- 同名のプロジェクトやタスクでも会話が混ざらず、プロバイダ切り替え後も同じチャットIDを使う。
- 同時作成、アーカイブ、削除、途中停止からの復旧で参照の重複や履歴欠落が起きない。
- 旧データの移行前後で発言と再開情報が一致し、過去イベントからの参照も解決できる。
- 参照先の欠落、ID衝突、破損JSON、書き込み失敗を検出して既存データを保全する。
- 標準の `bun run test` を実行し、実データは移行後の読戻しと参照検証が完了してから旧ファイルを削除する。
