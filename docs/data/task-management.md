# タスク情報のDB集約

タスクの識別・状態の正本を、`projects/<projectId>.sqlite` に集約する。アプリDBはプロジェクト登録とチャット参照、ジョブを管理する。

## 保存と通常操作

プロジェクトDBの `tasks` テーブルにID、名前、フェーズ、状態、作成日時、更新日時を保存する。IDは既存の `7100` 規則を維持する。旧文書の比較基準 `documentBaseline` と完了処理の復旧情報 `pendingCompletion` も引き継ぐ。不明な日時は `null` とする。列名は `id`、`name`、`phase`、`status`、`created_at`、`updated_at`、`document_baseline`、`pending_completion` とし、追加情報はJSONで保存する。

タスク一覧・取得・作成・改名・フェーズ遷移・完了・再開・削除はDBを使う。タスク情報と同じプロジェクトDB内のイベント・文書変更は同じトランザクションで確定する。チャット参照とワークフロージョブはアプリDBに属するため、DB間の更新は復旧情報を使い、途中停止や再試行で欠落・重複を起こさない。

タスク完了時は状態・完了イベント・ジョブ登録の入力をプロジェクトDBで確定し、アプリDBへの同じ完了回のジョブ登録が確認できた後に復旧情報を取り除く。未登録の完了処理が残る間は再開・削除の前に復旧する。

新規タスクでは `task.json` を生成しない。タスクの存在判定にフォルダーを要求しない。会話は既存のチャット管理を通してID参照し、文書はプロジェクトDBに保存する。作業や旧文書取り込みに必要なディレクトリは必要時に作成する。

タスク削除では現在のタスク情報とタスクの会話を削除し、イベント・文書の履歴・処理済みワークフロー会話は既存の保持方針に従う。実行中や未処理ジョブの削除制限を維持する。再起動で削除済みタスクが残存フォルダーから復活しないようにする。

## 移行

1. 登録済みプロジェクトごとに旧 `tasks/<taskId>/task.json` と作成・削除の復旧記録を検証する。ID、所属、形式、リンク、競合を確認する。
2. 旧タスクの全項目をプロジェクトDBへ保存し、移行元と保存結果の対応を記録する。既存の新しいDB値を再試行で上書きしない。
3. 保存結果を読み戻し、内容、文書、会話参照、完了処理の復旧情報が維持されていることを確認する。
4. 移行元が変化していないことを再確認して、検証済みの旧JSONだけを削除する。空になったタスクフォルダーと `tasks/` も削除する。旧Markdownや管理外のファイルが残るフォルダーは保全する。

Beni停止中に `bun src/backend/migrate-tasks.ts` を実行して実データを移行する。保存先は通常起動と同じ `BENI_DATA_DIR` を使う。先にプロジェクトDBの配置移行を完了させる。旧チャットも残っている場合は、続けてチャット移行を行ってからタスクJSONを移行する。通常起動では未移行のタスクJSONを検出したプロジェクトの操作を停止し、移行コマンドを案内する。移行中は対象プロジェクトの自動処理を開始しない。途中停止から同じ処理を再開できるようにする。破損や競合がある場合は元データを残して失敗を報告する。旧Markdownだけのタスク復元は従来の規則で一度DBに取り込み、移行済み・削除済みタスクを重複登録しない。

## 検証

全タスクのID・名前・日時・フェーズ・状態・追加情報の一致を確認する。会話のIDと内容、既存イベントと文書版を維持する。通常の作成から完了・再開・削除、再起動、移行再実行を偽エージェントで検証し、`bun run test` を実行する。実データでは読み戻しと参照照合の成功後に旧JSONと検証用コピーを削除する。
