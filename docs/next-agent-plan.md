# Beni 次期版：使用シーンと全体仕様

## 目的

ユーザーが希望やこだわりを自然に伝え、細部をすべて追わなくても作業を任せられるコーディングエージェント。操作画面は WebUI。指示と作業の結果を振り返り、蓄積した知見で指示や作業方法を改善する。

## 動作条件

Beniのバックエンドは一つだけ起動して利用する。二つ目以降を同時に起動した場合の動作は保証しない。これはデータ保存に限らず、Beni全体の動作条件とする。複数起動の検出・防止、プロセス間のロック、所有権の移譲、二つ目を閲覧専用にする機能は実装対象とせず、今後の対応予定にも含めない。

一つのバックエンドにPC・スマートフォン・複数ブラウザーから接続する利用は対応範囲に含む。

## 1タスクの流れ

1. **希望を伝える**：ユーザーがテキスト欄にラフな依頼や追加の希望を順不同で入力する。軽量モデルが指示書の Markdown を更新し、蓄積した手順や知識を参照する。書式にも気を配り、疑問や情報不足があればユーザーへ質問する。指示原文、確定事項、未確定事項、制約、完了条件を区別して残す。
2. **計画を作る**：ユーザーが指示書を確認し「確定」ボタンを押す。高性能モデルは検討状況や判断理由を見せ、実装計画を Markdown で作る。不明点は質問し、ユーザーからの不満や追加希望を反映する。
3. **実行を任せる**：ユーザーが計画を確認し、実行指示ボタンを押す。指示書と計画の版、および承認を関連づけて残す。高性能モデルがサブエージェントに作業を割り当て、進捗の監視、レビュー、添削、フィードバックを行い、完了まで面倒を見る。
4. **必要に応じて質問する**：高性能モデルが自分で判断して進めるかユーザーに委ねるかを判断する。質問が必要な疑問は質問欄に選択肢と自由入力欄を出す。回答が必要な作業は待ちつつ、依存しない作業は並列に進める。回答は計画や進行中の作業に反映する。指示書や計画に変更があった場合、再計画や確認が必要かを高性能モデルが判断する。
5. **結果を確認し、必要なら繰り返す**：完了をユーザーへ伝える。ユーザーがこだわりや修正希望を返したら、高性能モデルが改めて実装計画を作り、確認・実行の流れに戻る。タスク完了後は新しいタスクを作って最初から始める。

ユーザーは細かい部分を常に確認するとは限らず、関心やこだわりのあるところを見る前提とする。画面では進捗、判断が必要なこと、こだわりへの対応を分かりやすく示す。

## 画面の使い方

1. ユーザーがタスク名を入力し、「タスク作成」を押してプロジェクト詳細画面を開き、作成したタスクのチャットを表示する。
2. プロジェクト詳細画面には、チャットと Markdown プレビューを左右に並べる。ユーザーがチャットで希望を伝えると、指示書のプレビューが更新される。
3. LLM はチャット内で質問する。選択肢・数値・日付・シークレットなど専用の入力部品が適した場合はそれを使い、適切な部品がなければ通常のテキストで聞く。ユーザーはチャット欄から回答する。
4. フェーズインジケーターで「タスク内容」「実装フロー」「実装中」などの現在地を示す。フェーズが変わっても同じプロジェクト詳細画面を継続して使い、必要に応じて計画などの Markdown をプレビューする。
5. フェーズごとに使う LLM モデルをユーザーが選び、その選択を記録する。フェーズの切り替え時には、ユーザーの選択を踏まえて、どのモデルがユーザーと対話するかも判断させる。

## 判断と権限の改善

高性能モデルが質問すべきか自律的に判断する。判断や質問の仕方に対するユーザーのフィードバックを蓄積し、任せてよいことや確認が必要なことを「権限 MD」に育てる。ユーザーの判断とモデルの提案は区別し、未確認の内容を確定扱いにしない。

## ナレッジを手順書に育てる

- 実行中の質問や手戻りについて、指示、実際の行動、質問・回答、修正指示と結果を関連づけて記録する。記録時に LLM が緊急度を付け、更新時期の判断に使う。なぜ事前に確認できなかったかも分析し、事実と原因の仮説は分ける。
- 高性能モデルがナレッジ DB の記録を整理し、LLM 向けの手順書を適切な単位に分けて複数作成する。各手順書の内容を監修・手直しし、次のタスクで必要なものを参照できるようにする。
- フェーズ切り替えごとに、未反映の知見を裏で確認する。更新は基本的にタスク終了時とし、緊急度、未反映の量、更新コスト、モデルの使用制限、ユーザーの稼働時間を考慮して、早めの反映やまとまった整理時間が必要かを LLM が判断する。小さな更新を頻繁に走らせる無駄も考慮する。DB に保存するユーザーの指示・返答の時刻と内容を分析し、稼働傾向を LLM 自身が判断する。分析方法も LLM が考え、ユーザープロファイル MD に反映する。ユーザーが不在の間も、利用枠を調整して、作業ができるだけ途切れず平準化されるようにする。稼働時間は推定であり、各記録・MD の保持方法や分析の具体的な指標は今後検討する。
- 手順書・権限 MD・ユーザープロファイル MD などの分析手法をまとめた MD も作り、分析の方法を記録・改善する構想。どの単位で管理するかは今後検討する。
- ナレッジや手順書・権限 MD は Git で管理する。整理やコミットは LLM に任せ、ユーザーは必要なときに差分や履歴を確認できる。
- 既に解決・手順書への反映が済んだ記録は、削除、圧縮、アーカイブを検討する。元の根拠を追えるようにするため、まずは反映済みとして残す案を考える。保存期間や削除の判断は未決定。

## 大まかな構成と実装順の案

まず LLM 連携とチャットを実装し、会話できる状態を作る。その後、指示書・計画の Markdown、実行と監修、質問欄、履歴・ナレッジ DB、手順書の整理機能へ段階的につなぐ。[LLM チャット連携](features/llm-chat.md)を参照。

Claude Code は Agent SDK の `query()`、Codex は app-server を使い、ユーザーがインストール・ログイン済みの CLI に接続する。Beni は状態確認と更新操作を提供し、未ログインならログインを案内する。チャット履歴は当面、確認しやすい JSON ファイルに保存する。最初の動作確認に使う接続先はユーザーが決める。ChatGPT の直接連携や通常 API は将来の追加候補とする。モデル呼び出しと作業環境での実行を区別し、担当との対応は今後決める。接続状態を見て設定できる WebUI を設ける。ナレッジの参照方法もスキルか MCP か未決定。
