# 実行ファイルと自己開発

Beni のサーバー、画面の HTML・JavaScript・CSS、Bun ランタイムを一つの実行ファイルにまとめます。対象は macOS / Apple Silicon です。ビルド済みの Beni から自身のリポジトリを編集しても、稼働中の画面やサーバーはビルド時の内容を使い続けます。

## ビルドと生成物

リポジトリで依存関係をインストールし、Bun 1.4.4 以上で実行します。

```sh
bun run test
bun run build:exe
```

`build:exe` は既存の Vite・Tailwind の画面ビルドと、Bun による実行ファイルの生成を行います。ビルドのたびに `dist/executables/<build-id>/beni` を新しく生成し、過去の実行ファイルは上書きしません。`--version` でビルドの識別情報を確認できます。未コミットの変更があるビルドは dirty として区別します。

```sh
./dist/executables/<build-id>/beni --version
./dist/executables/<build-id>/beni --help
```

`<build-id>` はビルドの出力に表示された値へ置き換えます。バージョン・ヘルプの表示ではデータ領域を作成せず、エージェントへ接続しません。

生成物にはアプリのソースと依存パッケージ、画面の生成物をまとめます。実際の保存データ、認証情報、環境変数の値は含めません。起動にはリポジトリ、`node_modules`、外部の Bun は不要です。Codex・Claude の CLI とログイン状態は同梱しません。エージェントを使う場合は、起動した環境の `PATH` から公式 CLI を検出します。

ソースのビルド・テストには引き続き Bun と開発用の依存関係が必要です。実行ファイル化しても、Beni 内で自身をビルドする環境から Bun を削除するわけではありません。

## 保存先と起動

リポジトリのフォルダーでは、次のコマンドで最新のビルド済み実行ファイルを起動できます。

```sh
bun run app
```

初回は `bun run build:exe` で実行ファイルを作ります。`app` 自体はビルドしません。更新するときは再ビルドし、外部ターミナルで起動中の Beni を Ctrl+C で停止してから、もう一度 `bun run app` を実行します。起動後に新しいビルドを作っても、稼働中の Beni は元の実行ファイルを使い続けます。

実行ファイルのあるフォルダーで、次のコマンドだけで起動できます。

```sh
./beni
```

データは自動で `~/Library/Application Support/Beni/data` に保存します。実行ファイルを移動したり、別のディレクトリから起動したりしても保存先は変わりません。保存先を変える場合だけ `BENI_DATA_DIR` を指定します。相対指定は起動時の作業ディレクトリを基準にするため、運用では絶対パスを指定します。

通常は `http://127.0.0.1:3210/` を開きます。`BENI_PORT` と `BENI_PUBLIC_ORIGIN` はソース起動と同じです。Tailscale 経由の公開は [README](../README.md#tailscale-経由で起動する) の手順に従い、起動コマンドだけを実行ファイルへ置き換えます。

実行ファイル版は起動ディレクトリの `.env` や `bunfig.toml` を自動では読み込みません。環境変数は外部ターミナルや起動用スクリプトで設定してください。

リポジトリ内の既存データを使うときは、既存の Beni を停止してからデータ領域全体をバックアップし、上記の既定保存先へ移します。移動先に既存データがある場合は混ぜず、別の保存先を `BENI_DATA_DIR` で指定します。起動時の自動移行は行わず、`BENI_DATA_DIR` の変更だけでもデータは移動しません。v0.2.0 より前の非互換データを利用する手順ではありません。

## 生成物の検証

ビルド後、生成された実行ファイルを指定します。

```sh
bun run test:exe ./dist/executables/<build-id>/beni
```

検証用スクリプト自体は Bun を使います。実行ファイルをリポジトリ外の一時領域へコピーし、専用の保存先・作業フォルダー・空きポートで起動します。CLI の検索先を偽エージェントに限定して、実サービスを呼ばずに確認します。検証が終わったら、一時バックエンドと一時ファイルを片付けます。

運用中の保存先や作業フォルダーを候補版の検証へ流用しないでください。保存データに実行待ちのワークフローがあれば、起動後に処理が再開される場合があります。実データのコピーを使った検証も、この自動検証には含めません。

## Beni から Beni を修正する

1. 検証済みの実行ファイル A をリポジトリ外へコピーし、macOS の外部ターミナルから起動します。運用データもリポジトリ外の固定ディレクトリに置きます。
2. Beni に自身のリポジトリを作業フォルダーとして登録し、タスクを作成します。実装中・反省会のエージェントは、登録したソースを編集します。
3. 修正後に `bun run test`、`bun run build:exe`、生成物を指定した `bun run test:exe` を実行します。これらは Beni 内のターミナルからも実行できます。稼働版 A はソースや `dist/frontend/` の変更を読み込みません。
4. 候補 B を別のリリースディレクトリへコピーします。A を残し、どちらの `--version` も確認します。
5. エージェント、ワークフロー、ターミナル内の作業が終了したことを確認します。外部ターミナルで A を停止し、プロセスの終了を確認してから運用データ全体をバックアップします。
6. B を起動し、ブラウザーを再読み込みします。既定の保存先は A と共通です。保存先・ポート・公開 Origin を変更していた場合は A と同じ設定で起動します。保存されたプロジェクト、タスク、会話を確認して次の修正に進みます。

配置例は次のとおりです。`BENI_CANDIDATE` の `<build-id>` を実際の値に置き換え、リポジトリ内で実行します。

```sh
BENI_CANDIDATE="$PWD/dist/executables/<build-id>/beni"
BENI_RELEASE_DIR="$HOME/Applications/Beni/releases/$(basename "$(dirname "$BENI_CANDIDATE")")"
mkdir -p "$BENI_RELEASE_DIR"
cp -n "$BENI_CANDIDATE" "$BENI_RELEASE_DIR/beni"
"$BENI_RELEASE_DIR/beni" --version
```

次は **Beni 内のターミナルではなく、外部ターミナルで** 行います。稼働版を起動した外部ターミナルで Ctrl+C を押し、終了を確認します。別の外部ターミナルで同じ `BENI_RELEASE_DIR` を設定し、バックアップ後に候補版を起動します。

```sh
BENI_RUNTIME_DATA="$HOME/Library/Application Support/Beni/data"
BENI_BACKUP_DIR="$HOME/Library/Application Support/Beni/backups/$(date +%Y%m%d-%H%M%S)"
mkdir -p "$BENI_BACKUP_DIR"
cp -R "$BENI_RUNTIME_DATA" "$BENI_BACKUP_DIR/data"
"$BENI_RELEASE_DIR/beni"
```

この例は既定の保存先に運用データがある場合です。バックアップの成功を確認してから起動してください。保存先・ポート・Tailscale の設定を変えている場合は、従来の `BENI_DATA_DIR`・`BENI_PORT`・`BENI_PUBLIC_ORIGIN` も指定します。

Beni 内のターミナルはバックエンド停止時に終了するため、そこで停止から新版起動までを実行しません。生成中の回答やターミナルのプロセスを新版へ移す機能もありません。自動更新・自動再起動は行わず、切り替え時には一時的に接続が切れます。

## 旧版へ戻す

候補版に問題があれば外部ターミナルから停止し、必要に応じて候補版で更新されたデータも別途保存します。その後、切り替え前のデータのバックアップと、それに対応する旧実行ファイルを組み合わせて起動します。データ形式が変わっている場合、実行ファイルだけを戻しても復旧できません。

運用データを二つのバックエンドから同時に開かないでください。更新ジョブやエージェントの実行状態については、バックアップの復元によって実際のファイル変更まで巻き戻るわけではありません。切り替え前に作業を完了させることが前提です。
