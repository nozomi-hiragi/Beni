# 保存形式とファイル差分

## 保存場所

対象プロジェクトの `.beni/project.sqlite` とする。Beni本体のSQLiteとは分け、プロジェクトごとのイベント、文書の版、ナレッジ、精査の進捗を保存する。移行済みのタスク文書は文書テーブルを正本とし、版と同じトランザクションで履歴を記録する。旧文書は初回移行までファイルから照合する。対象範囲は [全体方針](README.md#内容を追跡する文書) に従う。

旧名の `events.sqlite` は初回アクセス時にSQLiteの復旧を済ませてから `project.sqlite` に改名する。両方のファイルが存在する場合は処理を止める。

プロジェクトDB自身やそのWALなどはファイル監視の対象外とする。

## テーブル構成

| テーブル | 主な項目 | 用途 |
| --- | --- | --- |
| events | id、type、at、task_id、phase、operation_id、chat_id、send_id、tool_call_id、pack_id、details | プロジェクト内の操作順序とチャットへの参照 |
| file_changes | event_id、path、previous_path、previous_change_id、patch、after_hash | ファイルの差分と版の連鎖 |
| file_snapshots | change_id、content | 指定した変更後の全文キャッシュ |

移行済みの文書一覧は文書テーブルから取得する。旧文書は移行時にファイルシステムから読み取る。現在の一覧を重複管理する `files` テーブルは設けない。DBは変更・削除などの履歴を保持し、最後に記録した状態やハッシュが必要な場合は `file_changes` の最新記録を参照する。記録済みの状態と現在の実ファイルの状態は区別する。

イベントIDはプロジェクト内で増加する整数とする。記録順序を示し、並行操作の厳密な発生順序を保証しない。時刻とは別に扱う。開始・終了イベントは共通のoperation_idで結ぶ。

ファイルはプロジェクトルートからの相対パスで指定し、file_idは設けない。previous_change_idで版の連鎖を辿り、変更前ハッシュは前の変更のafter_hashから得る。リネームは変更前後のパスで履歴を繋ぐ。削除後に同じパスで作成されたファイルは、新しい作成イベントを履歴の起点とする。リネームは、明示的な操作情報で特定できる場合、または同じ照合内で内容が一致する削除と作成が一対一の場合に検出する。それ以外は削除と作成に分ける。

1ファイルの変更につき1イベントを記録する。同じツール実行による複数ファイルの変更は、共通のoperation_idで結ぶ。

## 差分の保存

| 操作 | 保存する内容 | 変更後ハッシュ |
| --- | --- | --- |
| 作成・初回観測 | 初版の全文（存在しない状態からの追加） | 本文のSHA-256 |
| 更新 | 追加・削除された内容を持つ可逆差分 | 更新後本文のSHA-256 |
| 削除 | 削除前の全文（存在しない状態へ戻せる差分） | null |

空ファイルのハッシュと「存在しない」を区別する。差分はunified diff形式（`---`・`+++`・`@@`と追加・削除行を持つ形式）で保存する。Gitへの依存や連携は不要。改行コードを正規化せず、末尾改行の有無も保持する。適用時は位置と変更前の内容を厳密に検証し、曖昧な位置合わせは行わない。適用後の本文バイト列をSHA-256で照合する。採用する生成・適用処理はLF・CRLF・混在改行・末尾改行なし・空ファイルで往復一致を検証する。

追跡する文書は1ファイル1MiBまでとする。超過時は追跡できない旨を通知し、黙って飛ばしたり記録済みハッシュを更新したりしない。再び範囲内になったら最後の記録済み版と照合する。未記録の超過版は復元可能とは扱わない。

初回観測以前の履歴は作らない。停止中の複数回の編集は、最後の記録済み版から次に観測した版への一つの変更として扱う。

## 過去の版を読む

相対パスと変更イベントIDで版を指定する。その版に属する作成イベントと版の連鎖を特定し、起点の全文から対象の版まで差分を順に適用する。現在の実ファイルから逆順に戻す方式を通常の取得経路にはしない。

1. 対象の版以前で最も近い全文キャッシュを使う。キャッシュがなければ初版を使う。
2. 起点の本文ハッシュを検証し、対象の版まで差分を順に適用する。
3. 各差分の適用後にafter_hashと一致することを確認する。
4. 本文・ハッシュ・存在状態を返す。参照のための復元では実ファイルを書き戻さない。

現在の実ファイルに未記録の変更があっても、履歴の取得は記録済みデータから行える。新たな変更を記録する場合は、最後の記録済み版を復元して現在の実ファイルと比較する。削除された版は「存在しない」を返し、削除前の版は同じ手順で本文を復元する。

キャッシュを検証できなければ、その起点を使わず自前の履歴から復元する。初版と差分からも復元できない場合は履歴破損として報告し、推測でつなぎ直さない。実ファイルを過去の版へ書き戻すUIや埋め込みツールは、提供しない。

## 全文キャッシュ

ファイルごとの変更回数が10回増えるごとに、その版の全文をキャッシュする。初版を変更回数0とし、その後の本文更新で数える。プロジェクト全体のイベントIDとは分け、リネームだけでは加算しない。削除後の再作成は新しい初版から数え直す。

最新の記録済み版からの距離に応じて、古い全文キャッシュの密度を減らす。

| 最新版からの距離（変更回数） | 残す間隔 |
| --- | --- |
| 0〜40 | 10回ごと |
| 41〜80 | 20回ごと |
| 81〜160 | 40回ごと |
| 161〜320 | 80回ごと |
| 以降 | 距離の範囲と間隔を同様に倍にする |

間隔は初版からの変更回数の倍数で判定する。例えば最新が変更160なら、変更20のキャッシュは40回間隔の範囲に入るため削除し、変更40は残す。初版は常に残す。間引くのはキャッシュだけで、差分やイベントを削除しない。

例として変更27の本文を取得するとき、変更20のキャッシュが残っていれば、そこへ差分21〜27を適用する。古い版ほど必要な差分数が増えるが、どの記録済み版も復元できる。

キャッシュは履歴から再生成できる補助データ。対象の変更への参照と全文を保存し、その変更のafter_hashで検証する。作成・間引きの失敗で履歴の正本を壊さない。同じSQLiteの `file_snapshots` に保存する。`change_id` は `file_changes.event_id` を参照して一意とし、`content` に全文を保持する。本文バイト列を維持できるようBLOBで保存する。別ファイルとの整合管理を増やさず、作成と間引きをDB内で管理する。

## タスク削除との整合性

タスク削除では [履歴保持の方針](README.md#タスク削除後の履歴) に従い、イベントと文書履歴を削除しない。タスク削除をファイルごとの削除差分へ展開せず、タスク削除イベントによって現在の存在状態と過去の記録を区別する。削除済みタスクの版指定による取得には、現存するtask.jsonを必須としない。

タスク削除後もtask_idなどの参照を保持できるようにする。現存タスクやチャットの削除に連動した履歴の連鎖削除は設けない。削除前の照合・保存が失敗した場合は、復元に必要な情報を失ったままタスク削除を進めない。

## 記録の整合性

ファイル変更イベントと差分・変更後ハッシュの追加は、一つのSQLiteトランザクションで確定する。差分とハッシュは同じ読み取り内容から作り、逆適用による復元を検証してから公開する。

実ファイルの書き込みとSQLiteは単一トランザクションにならない。未記録の変更は次回の照合で検出し、観測していない中間状態は保証しない。チャットとイベントDBも別保存なので、再試行はプロジェクト・会話・送信・ツール実行を識別できるoperation_idと開始／終了の種別で重複を防ぐ。片方の保存成功をもう片方の成功と見なさず、保存失敗を通知して再試行する。参照先チャットが削除済みの場合はその旨を返す。
