# Beni 全体仕様

## この文書の位置づけ

Beniの目的、動作条件、タスクの進め方を定義する。採用済みの仕様を記載し、画面・機能・データ・通信の詳細は各仕様書で定義する。仕様の確定と実装の完了は区別し、現在の実装状況はコードとテストで確認する。

未決定の案は [今後の検討事項](future-considerations.md) に記載する。そこにある構想を、採用済みの仕様や実装予定として扱わない。

## 目的

Beniは、Web UIでコーディングエージェントへの依頼、仕様整理、計画、実行、結果の確認を支援するアプリケーションとする。ユーザーが希望やこだわりを自然に伝え、細部を常に追わなくても作業を任せられるようにする。

ユーザーは関心やこだわりのある部分を中心に確認する。画面には進捗、確認が必要なこと、希望への対応を分かりやすく示す。指示と結果を振り返り、確定した学びを次のタスクへ引き継ぐ。

## 動作条件

Beniのバックエンドは一つだけ起動して利用する。二つ目以降を同時に起動した場合の動作は保証しない。これはデータ保存に限らず、Beni全体の動作条件とする。複数起動の検出・防止、プロセス間のロック、所有権の移譲、二つ目を閲覧専用にする機能は実装対象とせず、今後の対応予定にも含めない。

一つのバックエンドにPC・スマートフォン・複数ブラウザーから接続する利用は対応範囲に含む。

## プロジェクトとタスク

プロジェクトは、ユーザーが登録した作業フォルダーとする。一つのプロジェクトに複数のタスクを作成できる。タスクは個々の依頼を表し、文書、フェーズごとの会話、変更履歴を持つ。プロジェクト全体の相談には、タスクに属さないGeneralチャットを使う。

タスクでは、指示原文、確定事項、未確定事項、制約、完了条件を区別する。モデルの提案や推測を、ユーザーが確定した意図として扱わない。

詳細は [オブジェクト仕様](objects/README.md) に従う。

## タスクの進め方

| フェーズ | 目的と操作 | 対応する文書 |
| --- | --- | --- |
| 要件定義 | ユーザーが希望を順不同で伝え、モデルが目的・制約・完了条件を整理する。不明点はチャットで確認する | `requirements.md` |
| 仕様整理 | 対象ごとに追加Markdownを作り、調査資料と採用する仕様を分けて目次に載せる | `documents.md` と追加文書 |
| 実装手順 | 整理した要件と仕様をもとに、実装の順序と検証方法をまとめる | `implementation.md` |
| 実装中 | ユーザーが選んだ実装担当モデルが、実装手順に沿って実装・検証を進める | 準備したタスク文書を参照する |
| 反省会 | ユーザーが結果を確認し、未達・不具合・意図とのズレへの手直し、検証、振り返りを行う | `retrospective.md` |
| 終了 | モデルが反省会の会話と文書から、次のタスクに使える知識をプロジェクトのナレッジへ反映する | `knowledge.md`（DB文書） |

### 準備と開始

最初の3フェーズは、フェーズ名を選んで自由に切り替える。各フェーズの会話は独立し、タスク文書は共有する。フェーズを切り替えても文書や作業結果は巻き戻さない。

仕様整理の目次では、調査結果や比較案を「資料」、採用する挙動や条件を「仕様」に分ける。実装中に「仕様」の文書を作業対象リポジトリのドキュメントへ配置し、既存文書との整合を取る。「資料」はタスク内に残す。

ユーザーは実装手順を確認し、実装担当モデルを選んで「開始」を押す。開始には、初期テンプレートから編集された空でない実装手順と、利用可能なモデルが必要となる。開始条件はサーバーでも検証する。仕様整理・実装手順へ移ると、先行文書を参照して対象文書の作成・見直しを自動で始める。

### 実装と停止

実装担当モデルには、実装手順に従ってゴールまで実装・検証を進め、未達や実行できなかった検証を報告するよう依頼する。

実装中は進捗を閲覧し、操作は「停止」とする。チャットへの追加入力、モデル変更、フェーズ変更は行わない。指示の修正が必要な場合は停止し、実際の作業停止を確認して実装手順へ戻る。停止で文書や実装済みコードは巻き戻さない。

停止以外で実行が終了した場合は反省会へ進み、全フェーズの資料を自動で精査する。生成の失敗や結果不明も確認の対象とし、実行の終了だけでタスクの達成や完了を確定しない。ブラウザーの切断だけでは実行終了と扱わない。

### 確認、手直し、完了

反省会では、実装結果とタスク文書をもとに手直しと検証を依頼できる。準備フェーズへ直接戻す操作は設けない。実装中の会話は履歴として閲覧できる。

反省会の精査を終え、ユーザーが「タスク完了」を押すと終了フェーズへ進む。モデルがナレッジを整理する間、ユーザーはチャットの進捗と履歴を閲覧できる。ナレッジの版が確定するとタスクを完了し、バックグラウンドでインストラクションを更新する。完了後は「再開」で同じタスクの反省会を続けられる。別の依頼は新しいタスクとして作成する。

開始・停止・終了時の詳細な条件は [タスク仕様](objects/task.md) に従う。

## 画面と対話

ホームでプロジェクトとタスク名を指定してタスクを作成し、プロジェクト詳細画面を開く。同じ画面でフェーズを進め、チャットとMarkdownプレビューを左右に並べて、依頼・文書・結果を確認する。プロジェクトのターミナルもこの画面から利用する。

準備フェーズと反省会で必要な確認はチャットで行う。実装中と終了フェーズのチャットは閲覧専用とする。

画面構成は [プロジェクト詳細画面](screens/project-detail.md)、その他の画面は [ドキュメントの目次](README.md) に従う。

## 接続先、モデル、指示

ユーザーがインストール・ログイン済みのCodex CLIまたはClaude Code CLIに接続する。Beniは状態確認と再確認の操作を提供し、認証そのものは公式CLIに任せる。接続できない場合に、別の接続先や課金方式へ自動で切り替えない。

ユーザーは会話ごと、タスクではフェーズごとに接続先とモデルを選ぶ。実装担当モデルは準備フェーズのチャット用モデルと独立して、タスク単位で選ぶ。モデルの性能区分による役割の固定や、ユーザーの選択に代わる自動選択は前提にしない。

モデルには、アプリ共通の指示と現在フェーズの指示を渡す。準備フェーズ・反省会のタスク文書と終了フェーズのナレッジは、埋め込みツールで編集する。CLI による作業フォルダー内の文書・コードの編集は実装中と反省会に限る。General は読み取り専用とする。

接続方式と作業範囲は [LLMチャット連携](features/llm-chat.md)、指示の管理は [インストラクション管理](features/instructions.md) に従う。

## 記録とナレッジ

タスク文書はプロジェクト内のSQLiteを正本とし、本文を項目順に連結してMarkdownを組み立てる。会話はフェーズごとにJSONで保存する。変更イベントと文書の版を記録し、別フェーズでの変更を会話へ引き継げるようにする。保存内容と復元の規則は [データ設計](data/README.md)、履歴は [タスクの変更履歴](objects/task-events.md) に従う。

反省会では、事実、原因の仮説、次回の改善を区別する。今回だけの経緯はタスクの `retrospective.md` に残し、終了フェーズで再利用できる確定した学びをプロジェクト共通のナレッジ文書に蓄積する。次のタスクで参照し、共通化できる行動ルールをインストラクションに反映する。 [要求・根拠を追跡できる文書管理](traceable-documents-design.md) / [プロジェクトのナレッジ](objects/project.md#ナレッジ)

## 旧試作の扱い

旧試作のコード・テスト・ドキュメントはGit履歴のコミット `05a0ade` にある `legacy/` を参照する。旧試作を参照しただけで、そこにある機能を現行仕様として扱わない。
